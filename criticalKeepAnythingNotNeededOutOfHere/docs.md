## 1. Goal and versions

Port iPadOS to the Mi Pad 3 with the XNU-port approach: own boot shim + patched open-source XNU 8796.141.3 + unmodified Apple userland from an IPSW.
Base device: iPad 7 Wi-Fi (iPad7,11, board J171AP, A10 = arm64), iPadOS 16.6.1 build 20G81. Gesture navigation: `/buttons home-button-type = 2`. IPSW page: https://ipsw.me/install/iPad7,11/20G81/ (DMGs: OS 096-57220-083, SystemOS 096-57381-083, AppOS 096-57613-084).

Stages (user's words): **Alpha** = now (preparation, nothing ran on the tablet). **Beta** = first boot. **Release** (always a stable branch) = some GPU acceleration (Metal not required), all 6 CPU cores, all 4 GB RAM, OTA through a custom app (A/B scheme; user wants a choice of iOS versions within the range the kernel supports), >= 50% stability (e.g. one hour without panic), full Setup Assistant (forced/bypassed activation, a real iCloud check will likely fail), general usability.
The port goes into the `userdata` partition and ERASES Android user data; system partitions are not written. Way back = stock Fastboot ROM. Idea (U, not decided): per-kernel branches or patch folders to support more iOS versions later.

Versioning: file `VERSION`, now **Alpha 0.1**. A new version needs at least 4 changed files (one file edited many times counts once). Hotfixes do not bump it. A version like 0.2.1 is the next one that brings something new. Kernel/shim version and the iOS userland version (16.6.1) are tracked separately (matters for OTA). History: Alpha 0.1 = M1 shim, MT8176 device tree generator, patches 0082 (GICv2) and 0083 (no LSE), launcher `cappu.py`.

## 3. Hardware: MT8176 (V from the Xiaomi sources, MiCode/Xiaomi_Kernel_OpenSource branch `cappu-n-oss`, `arch/arm64/boot/dts/xiaomi8176_tb_c9_n.dts` + `mt8173.dtsi`, unless marked)

- SoC MT8176: 4x Cortex-A53 + 2x A72 (dts says A57, specs say A72; real MIDR not read, U), ARMv8.0, **no PAC, no LSE**; PowerVR GX6250; 7.9" 1536x2048; no cellular; 64 GB eMMC.
- Interrupts: GIC-400 = **GICv2**: distributor 0x10221000, CPU interface 0x10222000, hyp 0x10224000, vcpu 0x10226000. Timer armv8-timer, PPI 13,14,11,10; virtual timer INTID 27, physical NS 30.
- UART0 0x11002000 (MTK UART), SPI 83, 26 MHz, GPIO rx 113 / tx 114; Android console ttyMT0 921600n1.
- eMMC: **mmc0 = MSDC0 at 0x11230000, size 0x1000, GIC SPI 71**; clocks CLK_PERI_MSDC30_0 and CLK_TOP_MSDC50_0_H_SEL; in the cappu dts: bus-width 8, HS200/HS400 1.8 V, vmmc = mt6397_vemc_3v3, vqmmc = mt6397_vio18, non-removable. mmc1 0x11240000 and mmc2 0x11250000 exist in the SoC tree.
- Touch: FocalTech FT5x46 on I2C0 (0x11007000), I2C address 0x38. USB: SSUSB (mtu3 + xHCI) at 0x11270000, old USB0 at 0x11200000.
- RAM: dts says `memory@40000000` size 0x80000000 (2 GB); the hardware has 4 GB; how it is extended (LK?) is U. Reserved: 0x44400000 (0x80000 ram_console), 0x444f0000 (0x10000), 0x5ffff000 (0x2000).
- The kernel `Image` fields used for sanity: Linux 3.18.x aarch64, text_offset 0x80000. Android kernel uses PSCI via smc and an appended DTB; bootloader is MediaTek LK (not Qualcomm ABL). MT8176 uses the MT8173 MMC driver (`drivers/mmc/host/mediatek/mt8173/`, registers in `mt_sd.h`).
- iPad7,11 device tree (V, real IPSW 20G81 tree j171ap, saved as `research/j171ap.adt`): model iPad7,11, J171AP; `/product`: artwork-device-idiom pad, scale 2, graphics-featureset-class APPLE3; `/buttons` has no home-button-type (the generator adds 2). ## 4. Boot chain, boot image, framebuffer

- Chain: BootROM -> preloader -> LK -> kernel. (U) `bootopt=64S3,32N2,64N2` means 64-bit ATF at EL3 and the kernel starting 64-bit non-secure at EL2; `shim/start.S` already drops EL2 -> EL1.
- Boot image (V, compared across three TWRP images: `twrp.img` (sha256 6d4eaa92...b171), `twrp-3_1_0-cappu_b4.img`, `twrp-3_2_3-0-cappu-20180906-Kirhe.img`): Android header v0 (`ANDROID!`), page size 2048, kernel_addr 0x40080000, ramdisk 0x49000000, second 0x40f78000, tags 0x4e000000, cmdline `bootopt=64S3,32N2,64N2 androidboot.selinux=permissive buildvariant=eng`, kernel = gzip(Image) + appended DTB (Image.gz-dtb), no 512-byte MTK headers, ramdisk = gzip cpio. First two TWRPs carry the same 3.18.35 kernel and byte-identical DTB; Kirhe has 3.18.121. DTB compatible `mediatek,xiaomi8176_tb_c9_n`, `mediatek,mt8173`; `/chosen` is empty in the file (LK fills it at boot).
- Build our image: `python3 tools/mkboot_mt8176.py --ref twrp.img --shim shim/mt8176/out/Image -o m1-boot.img [--raw]`. Params and DTB come from `--ref`, kernel is replaced by our shim, ramdisk empty. Only for `fastboot boot`, NEVER flash into boot/recovery. `--raw` is the fallback if LK rejects gzip (U). Ready images in `dist/`.
- Framebuffer (V, `drivers/misc/mediatek/video/mtdummy/mtkfb.c`): LK puts the screen data into the DTB `/chosen` (depth 1): property `atag,videolfb` = `struct { u64 fb_base; u32 islcmfound; u32 fps; u32 vram; char lcmname[]; }`, plus separate `atag,videolfb-fb_base_h/-fb_base_l/-islcmfound/-islcm_inited/-fps/-vramSize/-lcmname`; fps 0 means 6000. So the address is read from the DTB, never hardcoded. (U) LK adds it to OUR image's DTB; pixel format and stride (probably 32 bit, stride width*4); LK does not blank the display before the handoff.
- GICv2 instead of GICv3: shim has `shim/gicv2.h` (distributor and CPU interface init, ack/EOI, SGI). XNU needs: no `HAS_GIC_V3` branch, IAR/EOIR through MMIO (GICC), IPI through GICD_SGIR (8-bit target mask), banked GICD_ISENABLER0/IPRIORITYR0 per core, device tree GIC node and interrupt-parent rewritten, virtual timer INTID 27. (U) in which security state the kernel starts (affects GICD_IGROUPR).

## 6. Brick safety (priority 1)

Rules (V = general MTK scheme, U = not checked on this board):
1. NEVER write preloader / boot0 / boot1 (eMMC boot partitions) and never touch LK. While the preloader is intact the tablet can be recovered.
2. Install only into `userdata`; the boot image is temporary (`fastboot boot`, RAM only). Support for `fastboot boot` in this LK is U (forums confirm `fastboot flash recovery` and `fastboot -w` work).
3. Before ANY write: full backup of all partitions (especially preloader, nvram, nvdata, proinfo, seccfg, frp, lk, boot, recovery), two copies on the PC, checksums verified, recovery path tested BEFORE wiping anything. Tool: mtkclient (`mtk rl out`, `printgpt`, `dumppreloader`; MT8173 is in the SP Flash Tool bypass list, MT8176 support in mtkclient is NOT confirmed, U).
4. Emergency entry: fastboot = Vol- + Power at power-on or `adb reboot bootloader`; recovery = Vol+ + Power; mtkclient has BROM mode (volume buttons held while plugging USB) and Preloader mode (no buttons). Volume buttons work. Test both ways before erasing Android (U).
5. Xiaomi bootloader unlock may need Mi Unlock; sources disagree about waiting time (U); do it later, when there is something to install.
6. Check for a BROM entry and whether SLA/DAA authorization is needed (U).
7. OTA later: A/B scheme on eMMC, new image into the inactive slot, switch only after a successful boot, rollback on failure; OTA never touches pre-boot partitions.
Order before the first write: (1) find out if Android boots, adb works and the bootloader state (`fastboot oem device-info`); (2) full backup and checksums; (3) test the restore path; (4) only then temporary `fastboot boot`, and only after that userdata. Never write an installer that flashes userdata before the root FS, the eMMC driver (M2), backups and a working boot exist.

## 10. GPU and arm64e (ideas, nothing run)

- GPU (U, studied from Mesa docs, Phoronix, mesa-dev, LKML): Imagination has an open Rogue stack: Mesa Vulkan driver `powervr` (`-Dvulkan-drivers=imagination`) and the kernel driver `drm/imagination`; GX6250 was one of the first targets, developed on an Acer R13 Chromebook with MT8173 (a relative SoC). Mesa lists GX6250 BVNC 4.40.2.51 as "partially supported, not under active development" (Vulkan 1.2) and BVNC 4.45.2.58 as unsupported; the BVNC of our GPU is unknown (read it from GPU registers). Needs the binary Rogue firmware (linux-firmware). OpenGL ES through zink needed `PVR_I_WANT_A_BROKEN_VULKAN_DRIVER`. Path: 1) read the BVNC (shim or XNU) and compare with Mesa; 2) get the matching firmware; 3) an XNU kernel driver porting the `drm/imagination` logic (MMU/VA, command submission, power and clocks from the cappu dts; the main work, the Linux version was ~33.6k lines at v3); 4) Mesa (`powervr` + zink or direct GLES) in userland and replacing CoreAnimation's GL renderer (read Bergamota's `docs/` GPU research); 5) Metal on top, far away, not needed for Release. Risks: incomplete support of our BVNC, kernel driver size; CPU rendering must work first (Beta). Links: https://docs.mesa3d.org/drivers/powervr.html, https://www.phoronix.com/news/PowerVR-DRM-Driver-v3, https://asahilinux.org/2022/11/tales-of-the-m1-gpu/, https://github.com/ry-diffusion/Bergamota.
- arm64e: the donor iPad 7 (A10) is plain arm64 without PAC, so PAC is not our problem. Bergamota runs iOS 18 (arm64e) on a Snapdragon 845 without PAC by rewriting every arm64e Mach-O and the dyld shared cache with its tool **Renegade** (`tools/renegade/`: pacstrip, fips_rehmac, root build, HFS+; kernel xnu-11215, own bare-metal loader). So "arm64e userland cannot run without PAC" is wrong. If iPadOS 17/18 is ever wanted (A12+ devices), that path exists. SD845 has LSE and the A72 does not, so Bergamota does not settle LSE for us.
